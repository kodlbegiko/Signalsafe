# 會議 1｜2026-07-06

## A. 會議階段

**階段定位：問題探索與研究啟動。**

團隊當時已經有一個反詐騙互動訓練網站 POC，但使用者研究與問題證據不足。導師的首要任務不是要求更多功能，而是把團隊從「先做產品」拉回「先證明問題」。

## B. 當時產品狀態

POC 已具備：

- 前測。
- 詐騙情境題。
- 可疑／不確定判斷。
- 點選可疑處。
- 安全下一步。
- 約八題訓練。
- 後測。
- 學習紀錄。
- 曾構想班級／學校導入與排名。

## C. 導師核心診斷

### 1. 「詐騙」範圍太大

「詐騙」本身不是足夠精準的問題定義。需要進一步確認：

- 哪一類詐騙。
- 哪一類使用者。
- 詐騙流程中哪個節點最值得介入。
- 使用者為什麼在那個節點做出錯誤決策。

### 2. 詐騙是流程，不是單一訊息

應把詐騙拆成：

接觸 → 建立信任 → 情緒／需求刺激 → 操作引導 → 個資／金流 → 發現異常 → 求助／報案／隱瞞。

產品若只訓練「這是不是詐騙」，可能沒有處理真正危險的決策節點。

### 3. 不可用新聞印象替代使用者研究

不能因為某年齡層較少出現在媒體案例中，就推論他們較不容易受騙。可能存在通報偏差、羞恥感、選擇性報導等因素。

### 4. 產品已先做出來，因此更需要補證據鏈

需要建立：

> 真實問題 → 使用者研究 → 洞察 → 問題定義 → 解決方案 → Prototype → 使用者測試 → 成效／修正

## D. 研究方法要求

### 利害關係人

需納入：

- 學生／一般使用者。
- 受害者／曾差點受騙者。
- 家人與社交圈。
- 165／警政。
- 銀行／金融機構。
- LINE、簡訊、Facebook 等平台／通訊場域。
- 學校與教師。
- 詐騙集團／假帳號等負向利害關係人。

### 訪談

至少約三位真實對象；若困難，可使用二手資料補充，但不可完全由 AI 想像。

訪談應優先詢問真實事件：

- 最近一次遇到可疑訊息時發生了什麼？
- 當時做了什麼？
- 為什麼相信／不相信？
- 哪些線索有被注意／忽略？
- 誰影響了決策？
- 哪個時間點可能阻止錯誤行動？

## E. 對設計思考作業的要求

- Affinity Map：從逐字稿／觀察中找共同模式。
- Persona：由多個受訪者綜合，不等於其中一人。
- POV：使用者＋需求＋洞察，不可直接把解法寫進需求。
- Journey Map：應呈現前／中／後的行為、情緒、決策與介入點。

## F. 導師對產品的直接挑戰

評審可能問：

- 為什麼是網站？
- 為什麼是測驗？
- 為什麼是這個族群？
- 100 分是否代表不會被騙？
- 和既有防詐工具差在哪裡？

## G. 技術方向

會議中曾討論：

- 關鍵字／規則。
- 本機小模型。
- 雲端大型模型。
- 分層式架構。
- 裝置端／edge computing 與隱私可能性。

但這些不是當下最高優先級；研究與問題證據更重要。

## H. 會後 Action Items

- 完成利害關係人地圖。
- 明確定義目標族群。
- 至少三位真實使用者訪談。
- 蒐集二手研究與競品。
- 建立 Persona、Affinity Map、POV、Journey Map。
- 重新檢查前後測是否測到能力，而不是記住答案。

## I. 證據邊界

**已明確：** 產品需要使用者研究支持；AI 不可取代真實驗證；產品高分不等於真實防詐能力。

**尚未驗證：** 學生是否適合成為家庭防詐節點、家人是否更相信學生提醒、哪一族群最需要此產品。

# 會議 2｜2026-07-20

## A. 會議階段

**階段定位：把訪談與初步測試轉成可用產品洞察。**

第一次會議後，團隊已不再是完全沒有第一手資料，而是需要確認研究是否真的支持產品主張。

## B. 會前可確認產出

- 三位學生探索性訪談。
- U001–U003 匿名化管理。
- Persona。
- Affinity Map。
- POV／HMW。
- 前測／訓練／後測原型。
- 兩位完整前後測。
- 一位僅完成前測。

## C. 使用者研究主要發現

### 1. 學生不是完全沒有防詐知識

受訪學生已知道部分基本原則，例如：

- 不隨便提供個資。
- 對陌生來源保持警覺。
- 對照官方資訊。
- 詢問家人或可信任的人。

因此產品不能只是再講一次「不要點陌生連結」。

### 2. 真正缺口開始收斂為決策流程

可能更值得訓練的是：

- 在新情境中找出最關鍵的風險訊號。
- 知道當下最安全的下一步。
- 把原則遷移到不同詐騙變形。

## D. 測驗設計問題

### 1. 「全部選可疑」捷徑

如果題庫大量都是詐騙，使用者不必真正理解，就可能靠全部選可疑取得高分。

這會破壞：

- 判斷正確率的解釋性。
- 前後測有效性。
- 使用者是否真正具備鑑別能力的判斷。

因此後續必須增加正常／低風險對照情境。

### 2. `safe` 太抽象

單純用 safe／unsafe 容易讓測驗變成二選一猜題。

後續方向改為三分類：

- 有明顯風險。
- 資訊不足，需要查證。
- 目前較可信。

### 3. 計時不可直接等於能力

作答時間會受：

- 閱讀速度。
- 題目長度。
- UI 理解。
- 題型難度。

影響，因此不能單獨把「越快」當成「越會防詐」。

## E. 樣本與目標族群一致性

如果宣稱做給某族群，但研究樣本不是該族群，證據鏈會斷裂。

因此：

- 研究對象需與產品核心受眾一致。
- 只有學生樣本時，不可聲稱家庭／長輩效果已驗證。
- 家庭擴散只能暫列 extension hypothesis。

## F. Persona／POV／HMW 使用原則

- Persona 必須來自多位資料綜合。
- 必須區分受訪者原話、團隊歸納、團隊假設。
- POV 應描述真正需求，不把網站／AI 等解法直接塞進需求。
- HMW 保持 solution-open。

## G. 產品修正方向

### 日常訓練縮短

產品逐漸往：

短情境 → 快速判斷 → 立即回饋 → 一次抓一個核心重點。

### 安全下一步具體化

建議不再使用抽象「安全」，而是：

- 回官方 App／官網。
- 不點原訊息連結。
- 封鎖／檢舉。
- 求助家人／老師／可信任成人。
- 必要時撥打正式客服或 165。

## H. 會後 Action Items

- 修正三分類文字。
- 增加正常／低風險題。
- 重整計時與評量定義。
- 讓安全行動具體化。
- 保持目標族群與研究資料一致。
- 家庭共判先維持未驗證假設。
- 後續評量更重視新情境下的安全行動，而不是單純是否猜中「詐騙」。

## I. 證據邊界

**已可支持：** 學生已有部分防詐知識；原有題庫存在測驗捷徑；安全行動需要更具體。

**不可過度主張：** 已證明能提升真實世界防詐能力；已證明家庭共判有效；少數學生樣本代表全部學生。

# 會議 3｜2026-07-29

## A. 會議階段

**階段定位：停止發散、凍結研究規格、準備正式驗證。**

## B. 正式凍結項目

| 項目 | 當時決策 |
|---|---|
| 研究目標族群 | 16–18 歲高中階段學生 |
| 產品定位 | 防詐決策訓練系統 |
| 產品主次 | 訓練核心，急救輔助 |
| 日常訓練 | 最安全行動＋一個最重要訊號 |
| 研究輸出 | 行動＋三分類＋多選證據＋自信 |
| 首頁 CTA | 開始 90 秒快練 |
| AI | 後台輔助，不作前台最終判定 |
| 資料 | 匿名作答，聯絡資訊分離 |

> 注意：16–18 歲是當時正式研究驗證的凍結範圍，不等於產品未來永遠只能服務此年齡層。

## C. 為什麼要凍結

前期已出現：

- 目標族群持續變動。
- 功能不斷增加。
- OCR、AI、教師後台、家庭功能可能搶走核心。
- 研究與產品主張不一定一致。

所以後續原則是：

> 先用固定規格取得乾淨證據，再決定擴張。

## D. 產品核心

SignalSafe 不再主張自己是：

- 全自動詐騙判定器。
- 165 替代品。
- Whoscall 替代品。
- 系統級防護工具。

而是聚焦：

- 情境反覆練習。
- 找到關鍵風險。
- 選擇安全下一步。
- 發現個人盲點。
- 測量是否能遷移到新情境。

## E. 研究流程

正式評量包含：

1. 行動選擇。
2. 三分類判斷。
3. 多選證據。
4. 自信程度。

主要指標逐漸收斂為：

> **新情境下安全行動正確率。**

## F. 驗證階段

### Phase 1：Usability

- 約 8–12 位 16–18 歲學生。
- 先確認題目、介面、導航是否能使用。
- 不先宣稱教育效果。

### Phase 2：Immediate effect

- 約 20–40 位目標學生。
- 前測 → 訓練 → 立即後測。

### Phase 3：Retention

- 第 7 天延遲後測。
- 看是否仍保留判斷能力，而非只記住剛看過的教學。

## G. AI 與競品邊界

165、Whoscall、Google Messages、銀行與平台較適合處理：

- 辨識。
- 攔截。
- 查證。
- 系統／帳戶防護。

SignalSafe 處理：

- 練習。
- 安全決策。
- 個人盲點。
- 遷移。
- 保留測量。

AI 僅作後台輔助，不在前台聲稱「一定詐騙／完全安全」。

## H. 安全與研究完整性

- 功能 QA 不等於教育有效。
- 合成題目不可包裝成官方真實案件。
- 90 秒等門檻屬團隊假設，不是學術標準。
- 小樣本不可代表全部學生。
- 聯絡資訊和匿名作答資料分離。

## I. 不優先項目

- OCR 主軸。
- 前台 AI 自動判定。
- 完整教師後台。
- 排行榜。
- 複雜遊戲化。
- 大規模原生 App 重做。

## J. 會後 Action Items

1. 鎖定研究族群。
2. 固定題庫與研究版流程。
3. 做 usability。
4. 先修 UX／題意。
5. 再跑前測／訓練／後測。
6. 第 7 天延遲測量。
7. 分析主要指標與錯誤模式。
8. 簡報只使用實際證據支撐的主張。

# 會議 4｜2026-08-13

## A. 會議階段

**階段定位：從規格凍結走向產品意圖分流、可用性驗證與研究基礎設施分離。**

> 本次目前沒有完成逐字轉錄，因此以下內容主要整理「會後已反映到產品與研究設計中的明確收斂」，不將其全部標記為導師逐字指示。

## B. 會前狀態

已有：

- 90 秒快練。
- 完整前測／訓練／後測流程。
- 三分類。
- 多類風險線索。
- Learning Dashboard 概念。
- Emergency／可疑情況流程。
- Research session／匿名資料設計。

但 UI 已出現多個模式名稱與研究功能，存在「產品內部架構比使用者意圖更突出」的風險。

## C. 會後最重要的產品收斂

### 1. Intent before mode

一般使用者最需要回答的是：

- 我想練習。
- 我現在遇到可疑情況。

而不是先理解：

- Quick Mode。
- Full Assessment。
- Research Mode。
- Emergency Mode。

因此產品首頁應依意圖分流。

### 2. Safety before classification

真實事件的優先順序應是：

1. 停止新的高風險操作。
2. 離開對方控制的溝通／操作管道。
3. 改走官方或可信任來源查證。
4. 若已操作，進入止損與求助。

不能讓使用者為了「分類正確」而繼續留在危險流程。

可整理為：

> **STOP → SEPARATE → VERIFY**

### 3. Learn before automate

教育模式中仍然應：

情境 → 使用者先判斷 → 系統回饋 → 新情境再練。

不要讓 AI 在前台先把答案拿走。

### 4. Research is invisible infrastructure

研究需要：

- participant code。
- consent。
- session。
- reset。
- event log。
- export。
- pre／training／post。

但一般使用者不需要看到這些研究術語。

研究工具應退到後台／study URL，而非主產品首頁。

### 5. Tasks are independent

可用性研究的每個 task 應能單獨啟動與重置。

原因：如果 Task 2 失敗導致 Task 3–6 全部做不了，就無法判斷後面功能本身是否有問題。

因此研究記錄需要 task-level：

- start。
- completion。
- failure reason。
- event log。
- reset。

### 6. Evidence over decoration

Learning Dashboard 不應隨意顯示：

> 你的防詐能力 72 分

除非真的有可解釋、已驗證的量表。

更合理的是呈現：

- 常漏看的線索。
- 常做錯的安全行動。
- 特定情境弱點。
- 最近練習表現。

## D. Usability 與 Effectiveness 分離

第一階段先驗證：

- 看得懂首頁嗎？
- 找得到 Training 嗎？
- 找得到 Emergency 嗎？
- 三分類看得懂嗎？
- 安全行動能理解嗎？
- 結果頁知道下一步嗎？
- Dashboard 看得懂嗎？

這只能支持「產品可使用」，不能直接支持「教育有效」。

正式效果測試仍要保留乾淨 baseline。

## E. 題庫方向

本階段不再追求「題越多越好」，而是：

- 題意清楚。
- 正確答案合理。
- 安全行動唯一且可辯護。
- pre／post 難度相近。
- 測同一底層能力。
- 可測新情境遷移。

題庫需人工 review，不能只靠 automated test。

## F. 優先級

### P0

- 主入口不顯示 Research Mode。
- 明確 Training／Emergency 意圖分流。
- Emergency flow 真正可用。
- Training flow 保持完整。
- 研究任務可獨立執行。
- 修掉強制線性導航造成的 cascade failure。

### P1

- Learning Dashboard 重構。
- Event logging。
- Study URL。
- 題庫 schema／provenance 改善。

### P2

- OCR。
- 前台 AI。
- 完整教師後台。
- 進階 analytics。

## G. 會後 Action Items

### 產品

- 重構首頁資訊架構。
- Training／Emergency 依意圖分流。
- Research Mode 退到後台。
- 強化 emergency CTA 與 safety flow。
- 重構 dashboard。

### 研究

- 先做小型 usability pilot。
- 每個 task 可獨立執行。
- 建立 event logging。
- 保留版本／session provenance。
- effectiveness study 不被先前訓練污染。

### 證據

- 不把 usability success 當成教育效果。
- 不把 UI 分數當正式能力量表。
- 不把團隊設定的 threshold 當學術標準。

## H. 本次可信度邊界

**高可信：** 會後產品與研究明確朝 Training／Emergency 分流、Research 後台化、任務獨立、證據邊界等方向發展。

**需後續逐字稿確認：** 上述每一項是否為導師原話、由誰先提出、討論細節與語句脈絡。

# 後續引用規則

在複賽簡報／研究報告中：

### 可以寫

- 「第一次導師會議後，我們從先做功能回到使用者研究。」
- 「第二階段測試發現，全部選可疑可能形成測驗捷徑，因此加入正常對照。」
- 「第三階段正式凍結研究族群與主要指標。」
- 「第四階段進一步將 Training 與 Emergency 依使用意圖分流，並把研究功能移到後台。」

### 不應寫

- 「導師證明我們的方法有效。」
- 「導師認定 90 秒是最佳訓練時間。」
- 「四次會議已證明 SignalSafe 可以降低詐騙受害率。」
- 「第四次所有產品原則都是導師逐字要求。」

目前四次會議最完整、可防止過度宣稱的總結是：

> SignalSafe 的導師陪跑不是一路增加功能，而是持續把專案從「功能構想」往「問題證據、可測量決策、固定研究規格、可用產品入口與嚴格證據邊界」收斂。
